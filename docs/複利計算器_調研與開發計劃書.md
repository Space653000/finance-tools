# 槓桿複利決策引擎 — 從市場調研到上市計劃書

> 專案代號：**LeverCalc**（暫定）
> 版本：v0.1 草案　　日期：2026-08-01
> 適用對象：獨立開發者 / 小型團隊，使用 Claude Code 進行主要開發

---

## 0. 一頁摘要（先讀這頁）

**問題**：市面上的複利計算器只做兩件事——單筆複利、定期定額。但真實世界的投資人手上同時有：股票質押、理財型房貸、信貸、融資、甚至二胎三胎。這些負債各有利率、各有還款方式、各有斷頭條件，卻**沒有任何一個工具能把它們放在同一張表上算**。

**現況替代方案**：Excel 或 Google Sheets 自己拉。這才是真正的競爭對手，不是其他 App。

**核心洞察**：使用者要的不是「算出 20 年後有多少錢」，而是回答一個當下的決策問題——

> 「我現在借這 300 萬去投資，最壞會怎樣？大盤要跌幾趴我會被追繳？我撐得住嗎？」

**產品定位**：不是複利計算器，是 **槓桿部位的防禦邊界模擬器**。複利只是其中一個模組。

**差異化三支柱**：
1. **多層負債疊加** — 質押 + 房貸 + 信貸同時存在的統一模型
2. **防禦邊界（斷頭距離）** — 大盤還要跌 X% 觸發追繳、Y% 觸發斷頭，附壓力測試
3. **決策級 UI** — 一屏看懂，不是填 20 個欄位

**警語**：這個 App 的本質是「讓人更容易評估借錢投資」。設計倫理與法規合規不是附加項，是**產品的一部分**（見第 7 章）。

## 1. 市場研究與洞察

### 1.1 釐清問題（研究目標）

| 編號 | 待驗證假設 | 若成立的意義 | 若不成立的意義 |

### 1.3 初級研究（3–4 週）

**深度訪談（8–12 人，每人 45–60 分鐘）**

分層抽樣，四種人各 2–3 位：

1. **純新手**：只做定期定額，沒碰過槓桿
2. **質押實戰者**：有股票質押經驗，經歷過或擔心追繳
3. **房貸增貸投資者**：拿房子借錢投入市場
4. **從業人員**：理專、財務顧問、券商營業員（他們每天在幫客戶算這個）

**訪談腳本要點**（用 Jobs-to-be-Done 邏輯，問行為不問偏好）：

- 「請你回想上一次認真思考要不要借錢投資，那天發生什麼事？」
- 「你當時怎麼算的？可以打開給我看嗎？」（**請對方分享畫面，看真實檔案；務必事前取得書面同意，並提醒對方遮蔽帳號與金額等敏感資訊**）
- 「算完之後你有做決定嗎？什麼讓你猶豫？」
- 「有沒有哪一次算錯或算漏了什麼？」
- 「2022 年跌的時候你在想什麼？」

❗ 禁止問「你會不會想要一個 App 可以……」——沒有人能可靠預測自己未來的付費行為。

**量化問卷（目標 200–300 份）**

發放管道：PTT、Dcard、FB 社團、投資類 Podcast 聽眾。

必問題組：
- 目前持有的負債類型（複選）與大約金額級距
- 目前使用的試算工具（Excel / App / 券商網站 / 沒算）
- 最近一次投資決策卡住的原因
- 願付價格：以 Van Westendorp 價格敏感度四問法（太貴 / 貴但可接受 / 便宜 / 便宜到懷疑品質）
- **對每個候選功能做 Kano 模型分類**（必要 / 期望 / 魅力 / 無差異 / 反向）

### 1.4 競品分析

| 競品類型 | 代表 | 強項 | 弱點（我們的切入點） |
|---|---|---|---|
| 陽春計算器 App | 各類「複利計算機」 | 免費、開啟快 | 只有單筆+定額、廣告多、UI 粗糙 |
| 券商內建試算 | 各家 App 的試算功能 | 資料真實、免費 | 綁單一券商、不能跨帳戶、不算多層負債 |
| 專業級網站 | Portfolio Visualizer 等 | 功能深、有回測 | 全英文、桌機導向、學習曲線陡 |
| 財經數據平台 | 財經 M 平方等 | 數據豐富 | 貴、偏總經、非個人決策工具 |
| **試算表** | **Excel / Google Sheets** | **極度彈性、免費、已存在** | **難維護、易算錯、不能隨身、不能情境比較** |

**結論**：真正的對手是試算表。我們必須贏在**「彈性接近 Excel，但不用自己拉公式，而且在手機上兩分鐘算完」**。

**差異化定位語**：
> 別人算「會賺多少」，我們算「會不會撐不住」。

### 2.2 核心資料模型（這是產品的技術護城河）

不要用「單筆 / 定期定額」的舊思維切功能。用**四個原語**組合出所有情境：

```
情境 Scenario
├── 資產部位 Position[]
│     ├─ 標的（0050 / 00646 / 個股 / 自訂）
│     ├─ 期初金額、成本
│     ├─ 預期年化報酬、年化波動（可帶入歷史值）
│     └─ 配息率、再投入與否
│
├── 負債層 DebtLayer[]        ← 差異化核心
│     ├─ 類型：股票質押 / 房貸 / 理財型房貸 / 信貸 / 融資 / 二胎
│     ├─ 本金、利率（固定/機動）、期數
│     ├─ 還款方式：本息平均 / 本金平均 / 只繳息到期還本 / 寬限期
│     ├─ 擔保品連結 → 指向哪些 Position
│     └─ 風險門檻：維持率警戒線 / 追繳線 / 斷頭線
│
├── 現金流 CashFlow[]
│     ├─ 定期投入（可設調升率、暫停區間）
│     ├─ 不定期單筆進出
│     └─ 還款流出（由 DebtLayer 自動生成）
│
└── 約束 Constraint[]
      ├─ 維持率下限（如 130% / 166%）
      ├─ DBR 22 倍上限
      └─ 月付款佔月收入比上限
```

**引擎輸出**：

1. **淨值曲線** — 中位數 + 10/25/75/90 百分位帶（不是單一條線，單一條線是在騙人）
2. **防禦邊界儀表板**
   - 目前維持率
   - 距離追繳：大盤還需下跌 **X%**
   - 距離斷頭：大盤還需下跌 **Y%**
   - 撐過 N 個月不追加擔保品的機率
3. **槓桿淨效益** — 加權平均資金成本 vs 預期報酬，直接回答「這個槓桿划不划算」
4. **壓力測試（歷史重播）** — 把 2000 網路泡沫、2008 金融海嘯、2020 疫情、2022 升息循環的真實跌幅路徑套進來，看部位死不死
5. **情境並排比較** — A/B/C 三個方案同屏對照（這是 Excel 做不到的殺手級功能）

### 2.3 功能分級與 MVP 切割

**⚠️ 最大的專案風險是範圍失控。藍圖裡的東西不能一次做完。**

| 階段 | 功能 | 預估工期 |
|---|---|---|
| **V1 MVP** | 單筆 + 定期定額 + **單層質押** + 維持率警戒線 + 淨值圖 + 本地儲存 + 情境 A/B 比較 + 內建 ETF 歷史年化/波動（離線靜態資料） | 8–10 週 |
| **V2** | 多層負債疊加（房貸/信貸/二胎）+ 蒙地卡羅模擬 + 歷史情境重播 + 夏普值 + 訂閱制上線 + 雲端備份 | +8–10 週 |
| **V3** | 即時報價整合 + ETF 成分股權重展開 + 稅務與費用精算 + 跨裝置同步 + Web 版 | +12 週 |
| **審慎評估區** | 由 ROE/EPS 反推大盤與個股預估值 | 見 §7.1 法規風險，**建議延後或改為「使用者自行輸入假設」** |

> **關於「反推大盤指數預估」**：技術上可行（權重 × 個股預估 → 指數預估），但**輸出「預估值」極可能觸及投顧業務認定**。強烈建議 V1–V3 一律採「使用者輸入自己的假設，App 只做運算」的立場。App 是計算機，不是分析師。

## 3. 產品設計與開發

### 3.1 技術選型

**框架：Flutter**（建議）

| 考量 | Flutter | React Native |
|---|---|---|
| 圖表表現 | fl_chart / syncfusion，繪製控制力強 | 依賴 JS bridge，複雜圖表較吃力 |
| 計算密集 | Dart 原生執行，可用 Isolate 跑蒙地卡羅 | JS 執行緒易卡 UI |
| 雙平台一致性 | 自繪引擎，高度一致 | 依賴原生元件，差異較多 |
| Web 版延伸 | 支援（效能尚可） | 需 React Native Web |
| Claude Code 協作 | Dart 型別強、結構清楚，AI 產出品質穩 | 生態碎片化較多 |

**這個專案圖表重、運算重、UI 要精緻 → Flutter 勝出。**

**架構原則**

1. **計算引擎與 UI 完全分離** — 引擎寫成純 Dart package，零 Flutter 依賴，可獨立單元測試。這是整個專案品質的命脈。
2. **Offline-first** — 所有計算本地完成，無網路也能用。網路只用於同步與更新市場數據。
3. **金額一律用整數（分/厘）或 Decimal，絕不用 double 存錢**。浮點誤差在金融 App 是致命傷。
4. **狀態管理**：Riverpod
5. **本地資料庫**：Drift（SQL，適合情境的關聯結構）或 Isar

### 3.2 UI/UX 設計原則（針對使用者提到的三大痛點）

**痛點：「太簡單」「太複雜」「看不懂」→ 對應三個設計策略**

**① 漸進式揭露（Progressive Disclosure）**
- 開啟即見：三個欄位（本金、月投入、年數）+ 一張圖。新手 10 秒有結果。
- 「加入負債」是一顆按鈕，按下才展開複雜度。
- 專家模式開關，一鍵切換完整參數面板。
- **同一個 App 服務新手與老手，靠的是分層，不是妥協。**

**② 結論先行，過程可展開**
- 每個畫面最上方是一句人話結論，不是一堆數字：
  > 「大盤跌 23% 你會被追繳。以歷史來看，20 年內發生過 4 次。」
- 數字表格摺疊在下方，想看細節的人自己點開。

**③ 視覺化優先於表格**
- 主視覺是**面積圖**：資產（上）vs 負債（下），淨值是中間的差
- 追繳線 / 斷頭線畫成紅色水平虛線，跌破的區間直接標紅
- 用顏色語意化：綠=安全、黃=警戒、紅=危險。不要只用數字

**④ 即時回饋**
- 拖動滑桿，圖表即時重繪，無需按「計算」
- 這是相對 Excel 的體感優勢，必須做到位

**⑤ 情境並排**
- 「不借錢」「借 200 萬」「借 400 萬」三欄同屏
- 決策工具的本質是比較，不是單點計算

**設計流程**：紙上草圖 → Figma 低保真 → 找 5 位真人做可用性測試 → 高保真 → 再測 → 才開始寫程式碼。

❗ **不要跳過 Figma 直接讓 Claude Code 寫 UI**。沒有設計稿的 AI 產出 UI 會是「泛泛的漂亮」，不會是「這個產品該有的樣子」。

### 3.3 與 Claude Code 的協作方式

**專案初始化**

在 repo 根目錄建立 `CLAUDE.md`，寫清楚：
- 專案定位與核心資料模型
- 架構分層規則（引擎不得 import Flutter）
- 金額型別規範
- 命名慣例、測試要求
- 「每個計算函式必須附單元測試」

**任務切割原則**

| ✅ 好的任務 | ❌ 壞的任務 |
|---|---|
| 「實作 DebtLayer 的本息平均攤還表生成，含寬限期，附完整單元測試」 | 「幫我做一個複利計算器 App」 |
| 「維持率計算：給定 Position 與 DebtLayer，回傳當前維持率與距離追繳的跌幅百分比」 | 「把負債功能做一做」 |
| 「依照 figma-export.json 的規格實作 ScenarioCompareScreen」 | 「UI 做漂亮一點」 |

**建議開發順序**（由內而外）

1. 核心資料模型（Freezed 定義）
2. 計算引擎 + 單元測試（**先寫測試案例，用 Excel 手算驗證答案**）
3. 儲存層
4. UI 骨架
5. 圖表
6. 精緻化與動效

> **關鍵紀律**：計算引擎的每一條公式，都要有一個你手算過或用 Excel 對過的測試案例。AI 寫的金融公式**必須人工驗算**，這是不能外包的責任。

## 4. 測試與驗證

### 4.1 內部測試

**A. 計算正確性（最高優先）**
- 單元測試覆蓋率目標 ≥ 90%（僅限引擎層）
- 黃金測試集：20–30 組手算驗證過的標準案例
- 邊界測試：零本金、負報酬、利率 0%、期數 1 期、極端槓桿、除以零
- 與券商官方試算工具交叉比對質押相關數字

**B. 功能與相容性**
- Widget 測試 + 整合測試（integration_test）
- 裝置矩陣：iPhone SE（小螢幕）、iPhone Pro Max、中階 Android、平板
- 深色模式、動態字級、無障礙標籤

**C. 效能**
- 蒙地卡羅 10,000 次模擬須在 Isolate 執行，主執行緒不掉幀
- 冷啟動 < 2 秒

**D. 安全與隱私**
- 財務資料本地加密儲存
- 若有雲端同步：傳輸加密 + 帳號隔離
- **明確決定：預設不上傳任何財務數據**（這本身就是行銷賣點）

### 4.2 市場測試

**封閉測試（TestFlight / Google Play 內部測試軌道，20–30 人）**
- 從階段一的受訪者裡邀請，他們已經理解問題
- 觀察指標：完成一次完整試算的比例、卡在哪一步、平均耗時
- 每週收集一次回饋，兩週一個迭代

**可用性測試（5 人，錄影；須先取得受測者書面同意，錄影檔案於分析完成後刪除）**
- 任務：「假設你要用房貸借 200 萬買 0050，請算出大盤跌多少你會被追繳」
- 全程不給提示，只觀察。卡住的地方就是要改的地方
- 5 個人能找出約 85% 的可用性問題

**驗收門檻（未達標不上架）**
- [ ] 新使用者能在 3 分鐘內完成第一次有意義的試算
- [ ] 計算結果與黃金測試集 100% 相符
- [ ] 崩潰率 < 0.5%
- [ ] 至少 5 位測試者主動說出「這個我會用」

### 5.1 行銷 4P

**Product（產品）**
- 定位語：**「借錢投資前，先算你撐不撐得住。」**

- 免費層必須真的好用，否則沒有口碑

**Place（通路）**
- App Store + Google Play（雙平台同步）

## 6. 上市後追蹤與優化

### 6.1 監控指標

**北極星指標**：**每週完成至少一次「含負債層」完整試算的使用者數**
（不是下載數。下載數是虛榮指標。）

**輔助指標**

- 雙週發版節奏

## 7. 風險登記表（這章最重要，請認真讀）

### 7.1 🔴 法規風險（最高風險）

**問題**：台灣《證券投資信託及顧問法》對「證券投資顧問」有明確定義。提供**個股或大盤的預估值、目標價、投資建議**並收取報酬，可能構成須經許可的業務。

**藍圖中的高風險功能**：
- 由 ROE / EPS 反推大盤指數預估
- 個股預估值輸出
- 任何形式的「建議」「推薦」「應該買」

**緩解策略**：
1. **產品立場明確化**：App 是**計算工具**，所有預期報酬率、成長率**由使用者自行輸入**。App 不提供任何預測值。
2. **內建歷史數據僅呈現事實**（過去年化報酬、波動、夏普值），並明確標註「歷史數據不代表未來表現」。
3. **所有輸出標示為「模擬結果」而非「預測」**。
4. **上架前務必諮詢熟悉證券金融法規的執業律師。** 這筆錢不能省。
5. 服務條款與 App 內顯著位置置放免責聲明。

> 我不是律師，以上是風險提示而非法律意見。這一項請務必尋求專業協助。

### 7.2 🔴 產品倫理風險

**問題**：這個 App 會降低「借錢投資」的心理門檻。如果使用者依此決策後爆倉，責任問題與品牌傷害都很嚴重。

**緩解**：
- 預設參數保守（預期報酬預設值低、波動預設值高）
- 防禦邊界的視覺權重**必須大於**報酬預估
- 主動顯示壓力測試最壞情境，不要藏在深層頁面
- 高槓桿情境自動彈出警示，不可關閉
- **把「不鼓吹」變成品牌資產，而非合規負擔**

### 7.2b 🔴 研究過程的法遵風險

市場研究本身也可能踩線，三個最常見的：

| 風險 | 說明 | 做法 |
|---|---|---|
| **平台服務條款** | 爬取 App Store、Google Play、PTT、Dcard 等網站違反其條款，可能導致帳號受限 | 只用官方 API 或公開 RSS 端點，其餘人工閱讀 |
| **個人資料保護法** | 蒐集含帳號、暱稱的網路發文屬個資處理 | 只記錄去識別化的語彙與主題；訪談與錄影須取得書面同意並告知用途與保存期限 |
| **公平交易法** | 上市後若在行銷素材中指名比較競品，不實或引人錯誤的比較可能構成違法 | 競品分析僅供內部使用，對外行銷不指名競品，只陳述自家功能 |

### 7.3 🟡 資料授權與成本風險

即時報價與歷史數據的授權費用可能吞掉整年營收。

**緩解**：V1 使用公開來源（證交所開放資料）計算出的靜態歷史統計值，內建於 App，定期隨版本更新。即時報價延後到 V3 且商業模式驗證後再評估。

### 7.4 🟡 範圍失控風險

藍圖的野心遠大於 MVP 的合理規模。這是獨立開發者最常見的死因。

**緩解**：嚴格執行 §2.3 的階段切割。V1 沒做完不碰 V2 的任何一行程式碼。

### 7.5 🟡 App Store 審核風險

金融類 App 審核較嚴，可能要求：完整免責聲明、隱私權政策連結、明確的訂閱條款、資料來源說明。

**緩解**：預留 2 週審核緩衝，首次送審前逐條對照 App Store Review Guidelines 3.1（付費）與 5.1（隱私）。

## 8. 你原本流程遺漏的環節（補完版）

你的原始流程：
```
你 → Claude Code → Flutter App → 測試 → 修 Bug → GitHub → App Store
```

**這條線缺了「寫程式碼之前」與「上架之後」兩大塊。** 補完如下：

```
【前置｜寫任何程式碼之前】
市場調研 → 假設驗證 → 需求規格 → 資料模型設計 → Figma 設計稿
→ 可用性測試（紙上/低保真）→ 技術選型 → 法規諮詢
→ Apple/Google 開發者帳號申請（含公司需 D-U-N-S，耗時數週）

【開發｜你原本的部分，補上細節】
CLAUDE.md 專案規範 → 計算引擎（純 Dart + 單元測試）
→ 儲存層 → UI 實作 → 圖表 → 整合測試
→ CI/CD（GitHub Actions + Fastlane 或 Codemagic）
→ 崩潰監控（Sentry/Crashlytics）+ 分析埋點
→ 訂閱機制（StoreKit 2 / Google Play Billing）

【上架前】
隱私權政策 + 服務條款 + 免責聲明
→ App Privacy「營養標籤」填報 → 在地化（繁中/英/簡中）
→ 商店素材 + ASO 關鍵字 → TestFlight / 內部測試軌
→ 封閉 Beta（20–30 人）→ 送審（預留 1–2 週）

【上架後｜你完全沒提到的部分】
軟啟動 → 數據監控 → 評論回覆 → 雙週迭代
→ 客服管道 → 每年 iOS/Android 大版本相容性維護
→ 訂閱續訂率優化 → 內容行銷持續產出
```

**最容易被低估的三件事**：
1. **法規諮詢**（可能改變整個產品定義）
2. **設計階段**（跳過會導致無止盡的 UI 返工）
3. **上架後維護**（App 上架不是終點，是長期承諾的起點）
